# Desktop 普通需求验收

此流程不能用 `codex exec` 的成功替代。不要停止或重启正在工作的会话；只使用独立测试工程和新测试会话，推理档位为 low。

候选包先放在独立测试工程的 `.agents/skills`，项目级 `.codex/config.toml` 只连接隔离 registry 和候选 release；不放模型/provider/凭据，不修改用户级配置。由使用者在 Desktop 打开该工程并按需批准信任，选择 low，开始一个新测试会话。实际回执必须确认读取的是候选技能路径，并核对 `quality_info` 返回的候选版本；如果被用户级旧技能遮蔽或未暴露项目 MCP，记录为阻塞，不能声称候选通过。

先确认该新会话实际发现 `codex-workflow` 等七项技能，且有 `quality_info`、`quality_resource` 等工具。磁盘文件存在、`codex mcp list` 显示 enabled、独立 stdio 进程返回成功，都仅是就绪证据。工具未暴露时，应显示缺失/降级，不能声称调用成功。只有空闲且用户允许时才在设置中重新加载相应 MCP，不能为验收打断其他任务。

只输入业务需求，不加 `$skill`、技能名、MCP 名或“请调用某工具”：

> 帮我完成这个工程的 normalize_ids 去重功能。开始前先和我确认关键边界。

澄清答复：只接受有限 list[int]，拒绝 bool 和负数；非法容器 TypeError、非法元素 ValueError；保持首次出现顺序、不修改输入，空列表返回空列表。确认需求和具体计划后继续。

观察并保存实际会话回执：

1. 入口自动读取技能；实际调用 quality_info；报告能力和当前工作目录。
2. 需求→计划→独立计划复核→批准→已有/新隔离 worktree 实施；原工程未改。
3. 原生测试有原始输出；独立审计者身份与实施者不同。
4. 在临时测试工程植入已知缺陷，审计阻塞并交回原实施者；修复和回归测试后由独立评审者核对当前源码和证据。
5. 简单翻译“把 hello 翻译成中文，只回答译文”不触发该工程流程。

记录证据出处、实际身份、源码摘要及每一步 PASS/BLOCKED/UNVERIFIED。不得依赖模型自述“已经使用技能”。CLI 简要 JSON 可能遗漏首个原生调用，必要时核对该测试会话的原始配对调用/返回记录，不扫描其他聊天。

本轮由使用者在 Desktop 打开测试工程并输入需求，已完成普通需求入口、实施、独立审计和受控缺陷修复复验，结果见 [本轮报告](2026-11-19-hardening.md)。宿主电脑控制工具仍禁止操作 Codex；使用会话只读记录核验，没有绕过 UI 限制。跨对话消息不能替代目标要求的用户直接确认。
